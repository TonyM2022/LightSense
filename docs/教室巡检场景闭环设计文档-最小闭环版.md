# LightSense 教室巡检场景闭环设计文档

## 1. 文档目的

本文档用于将 LightSense 从“频闪检测仪”进一步扩展为“教室健康用光巡检系统”的**最小闭环版**方案。

目标不是一次性做大而全，而是在现有功能基础上，优先实现一条清晰、可演示、可答辩、可落地的业务闭环：

**新建教室巡检 -> 按标准点位测量 -> 自动汇总教室结论 -> 输出整改建议 -> 支持整改后复测对比**

本文档仅定义方案，不涉及当前程序代码修改。

---

## 2. 设计目标

### 2.1 核心目标

将现有系统从“单灯具/单记录测量”升级为“面向一间教室的标准化巡检流程”，让系统不仅能测出指标，还能回答以下实际问题：

1. 这间教室整体是否存在频闪健康风险？
2. 风险是局部问题还是整体问题？
3. 优先应该排查哪里？
4. 整改后是否真的改善？

### 2.2 设计原则

1. **最小可落地**：尽量复用现有测量、记录、趋势、CSV 能力；
2. **标准化流程**：固定点位、固定步骤、固定输出，保证横向可比；
3. **面向答辩展示**：让评委能看懂“发现问题到复核整改”的完整链路；
4. **面向后续扩展**：未来可平滑升级到完整巡检版、多教室版、云端版。

---

## 3. 当前基础能力

结合当前项目，LightSense 已具备以下可复用能力：

1. 实时测量 `Percent Flicker / Flicker Index / Pst^LM / SVM / 主频 / 光照均值`
2. 基于 `光照量程前置检查 + Pst^LM ≤ 1 + SVM ≤ 0.4` 的综合判定
3. 教室测量记录存储、标签管理、CSV 导出
4. OLED + 五键本地交互
5. 网页端展示、教室记录列表、趋势分析
6. 历史标签复用、日期记录、整改后的长期趋势跟踪基础

因此，“最小闭环版”不需要推倒重做，而是要在现有记录能力之上增加一层**教室巡检语义**。

---

## 4. 最小闭环版范围

### 4.1 纳入本期的功能

1. 一次巡检对应**一间教室**
2. 固定 **5 个标准测点**：中心 + 四角
3. 每个测点完成一次现有教室测量
4. 自动汇总出**教室级结论**
5. 自动生成**简单整改建议**
6. 支持**整改前/整改后**两次巡检结果对比

### 4.2 暂不纳入本期的功能

1. 多楼栋批量巡检调度
2. 自定义测点模板编辑器
3. 教室平面图自动绘制
4. 复杂专家诊断模型
5. 多角色权限/云端协同管理
6. 自动生成 PDF 正式报告

---

## 5. 场景定义

### 5.1 使用对象

1. 学校后勤/总务老师
2. 科创展示场景中的学生讲解员
3. 教室照明改造验收人员

### 5.2 使用场景

1. 新装或改造后教室验收
2. 日常巡检排查
3. 学生反映“灯看着不舒服”后的定位复查
4. 换灯或维修后的效果验证

---

## 6. 最小闭环业务流程

### 6.1 巡检流程

1. 选择或填写教室信息
2. 创建一条新的巡检任务
3. 系统提示按固定顺序测量 5 个点位
4. 每个点位完成一次测量并保存结果
5. 5 个点位全部完成后，自动生成教室汇总结论
6. 系统给出整改建议
7. 若后续再次对同一教室巡检，则自动归为“复测”，可做前后对比

### 6.2 闭环价值

这条流程把项目价值从“测一个点”升级为“完成一间教室的标准巡检与复核”，更符合比赛对“真实问题解决能力”的期待。

---

## 7. 标准测点设计

### 7.1 测点模板

最小闭环版固定采用以下 5 点：

1. 中心
2. 左前
3. 右前
4. 左后
5. 右后

### 7.2 设计理由

1. 测点数量适中，比赛演示和实际使用都可接受
2. 能覆盖教室空间分布差异
3. 能支持“局部异常”和“整体异常”的基础判断
4. 与“中心 + 四角”教室验收口径一致，便于答辩说明

### 7.3 测点命名规范

建议固定使用以下枚举值，避免自由文本带来统计困难：

| 编码 | 显示名称 |
|---|---|
| `C` | 中心 |
| `LF` | 左前 |
| `RF` | 右前 |
| `LB` | 左后 |
| `RB` | 右后 |

## 8. 数据模型设计

最小闭环版建议在现有“单条测量记录”之上增加两层结构：**巡检任务** 和 **巡检测点结果**。

### 8.1 巡检任务（InspectionTask）

表示“一间教室的一次完整巡检”。

建议字段：

| 字段 | 说明 |
|---|---|
| `task_id` | 巡检任务唯一编号 |
| `classroom_id` | 教室编号，如 `A302` |
| `classroom_name` | 教室名称，如 `三年级2班教室` |
| `building` | 楼栋，可选 |
| `floor` | 楼层，可选 |
| `scene_type` | 场景类型：验收 / 例行巡检 / 故障复查 / 整改复测 |
| `inspector` | 巡检人 |
| `date` | 巡检日期 |
| `status` | 未开始 / 进行中 / 已完成 |
| `summary_verdict` | 教室级判定 |
| `advice` | 整改建议 |
| `compare_prev_task_id` | 对比的上一轮巡检任务 ID，可选 |

### 8.2 测点结果（InspectionPointResult）

表示“一个巡检任务中的某个测点结果”。

建议字段：

| 字段 | 说明 |
|---|---|
| `task_id` | 所属巡检任务 |
| `point_code` | 测点编码，如 `C/LF/RF/LB/RB` |
| `point_name` | 测点名称 |
| `label` | 当前已有的灯具标签或测点标签 |
| `duration` | 测量时长 |
| `pst` | Pst^LM 均值 |
| `svm` | SVM 均值 |
| `m` | 波动深度均值 |
| `freq` | 主频 |
| `vavg` | 光照均值 |
| `verdict` | 单点判定 |
| `timestamp` | 测量时间 |

### 8.3 教室级汇总（InspectionSummary）

表示自动汇总出的巡检结论。

建议字段：

| 字段 | 说明 |
|---|---|
| `task_id` | 所属巡检任务 |
| `pass_count` | 合规测点数 |
| `fail_count` | 异常测点数 |
| `dark_count` | 光线过暗点数 |
| `bright_count` | 光线过亮点数 |
| `pst_fail_count` | Pst 超标点数 |
| `svm_fail_count` | SVM 超标点数 |
| `worst_point` | 风险最高点位 |
| `summary_verdict` | 教室级判定 |
| `advice` | 整改建议 |

## 9. 教室级判定逻辑

### 9.1 单点级判定

单点继续沿用现有规则：

1. 先看光照量程是否异常
2. 再看 `Pst^LM ≤ 1`
3. 再看 `SVM ≤ 0.4`

### 9.2 教室级判定建议

最小闭环版建议采用简单、可解释的规则：

#### A. 教室合规

满足以下条件：

1. 5 个点位全部合规  
或
2. 仅 1 个点位轻微异常，但复测可恢复

输出：

`教室整体低风险，建议定期复检`

#### B. 教室局部风险

满足以下任一条件：

1. 1 到 2 个点位异常
2. 异常集中在某一角或某一区域
3. 光照异常点与频闪异常点并存，但未形成普遍问题

输出：

`教室存在局部风险，建议优先排查对应区域灯具或驱动`

#### C. 教室整体风险

满足以下任一条件：

1. 3 个及以上点位异常
2. 中心点也异常
3. 多点均为同类超标（如普遍 SVM 偏高）

输出：

`教室存在整体性照明风险，建议统一排查该教室灯具驱动或供电质量`

### 9.3 最差点位输出

系统同时输出一个“最差点位”用于展示与复查，优先级建议：

1. 双超标
2. Pst 超标 / SVM 超标
3. 光线过暗 / 光线过亮
4. 其他风险程度较低点位

## 10. 整改建议库设计

最小闭环版不追求复杂专家系统，只提供规则明确的建议文案。

### 10.1 建议规则

| 触发条件 | 建议输出 |
|---|---|
| 全部点位合规 | 教室当前整体合规，建议按月或按学期复检 |
| 个别点位 SVM 超标 | 建议优先检查对应区域灯具驱动高频调制问题 |
| 个别点位 Pst 超标 | 建议优先检查低频纹波、电源或驱动稳定性 |
| 多个点位同类超标 | 建议排查该教室整批灯具或统一驱动方案 |
| 多点光照过暗 | 建议检查灯具老化、积灰、安装高度或测量位置 |
| 整改复测后明显改善 | 说明整改有效，建议纳入后续定期复检档案 |
| 整改复测后仍异常 | 建议继续更换灯具或进一步排查供电/驱动问题 |

### 10.2 建议文案风格

1. 用“建议排查/建议复测/建议优先关注”，不使用过度绝对化表述
2. 面向学校老师可读，不堆砌专业术语
3. 每次最多输出 1 到 3 条建议，避免信息过载

---

## 11. 整改前后对比设计

### 11.1 对比目标

证明系统不仅能发现问题，还能验证整改是否有效。

### 11.2 对比条件

当满足以下条件时，触发“复测对比”：

1. 教室编号相同
2. 测点模板相同
3. 存在上一轮已完成巡检

### 11.3 对比输出内容

1. 异常点位数量变化
2. 教室级结论变化
3. 中心点指标变化
4. 最差点位指标变化
5. 是否从“整体风险/局部风险”转为“合规”

### 11.4 建议展示文案

示例：

- `整改前 5 点中有 3 点超标，整改后仅 1 点超标，教室风险由“整体风险”下降为“局部风险”。`
- `整改后中心点 Pst^LM 从 1.42 降至 0.63，SVM 从 0.78 降至 0.21，说明整改有效。`

## 12. 页面与交互建议

最小闭环版建议在现有网页教室测量页基础上扩展，不单独做复杂新系统。

### 12.1 页面结构

建议增加四个区域：

1. **巡检任务区**
   - 教室编号
   - 教室名称
   - 巡检类型
   - 巡检人
   - 开始巡检按钮

2. **测点流程区**
   - 当前应测点位提示
   - 已完成点位进度
   - 每点“开始测量/已完成”状态

3. **教室汇总区**
   - 5 点完成后自动显示教室级结论
   - 最差点位
   - 整改建议

4. **复测对比区**
   - 与上一轮巡检对比
   - 输出变化摘要

### 12.2 页面状态机

建议状态如下：

1. `idle`：未创建巡检
2. `task_created`：已创建巡检，待测第一个点
3. `measuring`：当前点位测量中
4. `point_done`：当前点位完成，等待下一个点
5. `task_done`：5 点全部完成，显示汇总结果
6. `compare_ready`：存在上一轮记录，可展示前后对比

### 12.3 OLED 最小支持

最小闭环版网页优先，OLED 只需提供辅助信息即可：

1. 显示当前巡检教室编号
2. 显示当前待测点位
3. 显示已完成点位数量
4. 巡检完成后显示教室级结论简版

## 14. 竞赛展示价值

“最小闭环版”虽然功能不算庞大，但对比赛非常关键，因为它补上了最打动评委的一环：

### 14.1 从仪器到方案

不是“我做了个检测仪”，而是“我设计了一套教室巡检与整改复核方案”。

### 14.2 从单点到全教室

不是“这个点超不超标”，而是“这间教室整体有没有问题，问题分布在哪里”。

### 14.3 从测量到治理

不是“测完就结束”，而是“测量 -> 判断 -> 建议 -> 复测”。

### 14.4 从技术展示到社会价值

更容易回答比赛中的高频问题：

1. 学校为什么需要它？
2. 老师怎么使用它？
3. 发现问题后怎么办？
4. 改完以后怎么验证？

## 15. 推荐实现顺序

最小闭环版建议按以下顺序推进：

### 第 1 步：巡检任务建模

先把“单条测量记录”组织进“一次巡检任务”的框架里。

### 第 2 步：固定 5 点测量流程

实现中心 + 四角的顺序化巡检流程。

### 第 3 步：教室级汇总判定

实现“局部风险 / 整体风险 / 合规”的教室级结论。

### 第 4 步：整改建议输出

接入规则化建议文案。

### 第 5 步：复测对比

实现同一教室前后两轮巡检的结论对比。

## 16. 后续扩展方向

在最小闭环版稳定后，可继续升级为完整版本：

1. 增加黑板区、讲台区等扩展点位
2. 支持批量教室巡检列表

5. 支持自动导出正式巡检报告
6. 支持灯具级寿命跟踪与维护计划

---

## 17. 结论

LightSense 当前已经具备很强的测量与展示基础。  
“教室巡检场景闭环”的关键，不在于增加更多指标，而在于把已有能力组织成一个完整可执行的流程。

最小闭环版的价值在于：

1. 工作量可控
2. 复用现有功能多
3. 比赛展示效果强
4. 能明显提升作品的“实际应用落地性”

建议后续开发优先围绕本文档的 5 点模板、教室级判定、整改建议、复测对比展开。
